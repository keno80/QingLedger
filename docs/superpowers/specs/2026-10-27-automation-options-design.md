# 自动记账新增选项设计（待确认）

日期：2026-10-27。基于 0.7.34 / d04bae6。本文是方案，不表示 Android 功能已经实现。

## 需求与兼容约束

1. 新增今日收支常驻通知。
2. 新增“确认后入账”模式，识别后弹出可编辑的确认窗口。
3. 接入“Shizuku + ADB”采集后端。

用户明确纠正“不是改，是新增”：保留现有直接入账，不把全部用户强制迁移为待确认。升级后现有入账方式保持“直接入账”。采集方式和入账方式独立配置；通知、无障碍和 Shizuku 使用同一入账决策。

## 方案选择

| 方案 | 行为 | 权衡 |
| --- | --- | --- |
| 悬浮确认 + 通知入口（推荐） | 已授权时在当前应用上方显示轻账弹窗；不能显示时保留候选并发送待确认通知 | 满足即时编辑，新增悬浮窗权限；无授权时仍可处理 |
| 仅通知进入确认页 | 识别后点通知进入轻账编辑 | 权限较少，但不会直接弹出窗口 |
| 仅轻账前台显示弹窗 | 其他应用内只保留待确认记录 | 干扰少，但用户容易错过，不满足即时弹窗预期 |

选择第一种作为拟实现方案。系统通知、悬浮窗及 Shizuku 均由用户手动授权；不使用全屏来电通知模拟记账弹窗。

## 设置和界面

沿用已确认的自动记账页，保留状态卡和现有导航。新增“入账方式”行，显示“直接入账”或“确认后入账”；底部 miuix 单选面板切换。新增“今日收支通知”设置，进入预览和开关；通知与自动记账总开关独立，暂停采集后仍可显示手动记账的今日汇总。

“权限与运行”新增“确认弹窗”授权状态，仅开启确认模式时强调配置。采集方式中的 Shizuku 从“开发中”变成配置入口：显示未安装、未启动、待授权、连接中、已连接、连接断开、能力不支持的真实状态。Root 保持原状态。

所有新增内容使用现有薄荷绿、miuix 卡片 / 分段 / 底部面板及等宽操作按钮，保留安全区与 24dp 末尾留白。不调整无关账本、统计或我的页面。

交互预览：[新增功能提案](../../qingledger-automation-options-preview.html)。实现获批后将相同入口和交互同步到 `docs/qingledger-ui-preview.html`。

## 今日收支常驻通知

- 标题“今日收支”，同一行展示“支出 ¥xx · 收入 ¥xx”，可带“待确认 n 笔”，点击打开今日账本。
- 采用账本时区的本日范围，使用完整数据库聚合，与账本统计一致：退款冲减支出，账户间转账不计收入 / 支出；删除账单和未确认候选不计入。
- 新增、编辑、删除、退款、导入、恢复及跨日后刷新。日期 / 时区变化重新计算日期范围；采用低打扰频道，不每次响铃。
- 使用独立通知 ID / 频道，不覆盖现有 Live Updates 识别进度 / 结果。锁屏默认隐藏具体金额，展开后遵循系统隐私设置。
- 开关关闭撤下此汇总。若 Shizuku 采集仍运行，其必要前台服务通知保留运行状态，不能以关闭汇总隐藏运行中的采集。
- 长时采集使用前台服务并声明实际用途；普通通知和前台服务仍受系统权限、用户停止和厂商后台管理影响，不承诺进程永不被结束。

## 确认后入账模式

### 数据与状态

识别出的合法交易先以结构化候选落库为 PENDING，随后才展示窗口或通知；此时不写正式账单，不改变余额 / 统计。候选保存来源、会话、识别时间、方向、实付金额、商户 / 对方、识别账户及原价 / 优惠，不保存截图或页面原文。

同一会话后续识别更新合并到同一候选，不新建多个待确认项；编辑中的字段由用户草稿优先，后台不得覆盖。因进程异常退出而未处理的候选可恢复；用户主动关闭的候选直接舍弃并保留去重标记，旧页回访不会再次自动弹出。已有正式账单沿用原去重关系；切换采集后端也不主动制造新交易。

点击“确认入账”在数据库事务中校验并写账，候选转 CONFIRMED。双击、重放通知和并发确认只能产生一笔。确认时使用用户修改后的值，并保留识别来源。明确金额或方向仍不足的事件继续跳过，不因新增模式就提示用户处理任意页面文字。

切换入账方式不自动提交已有待确认项。直接入账模式保持当前行为。模式切换通过配置代次隔离在途事件；已有待确认项保留到用户处理。

### 弹窗内容

标题“确认记账”，来源和待确认数量紧凑显示。可编辑字段：类型、金额、分类、资金账户、商户 / 对方、日期、时间、备注；支出可编辑原价 / 优惠，退款可关联原支出。日期使用已有日历，时间使用 miuix 滚轮。

底部左“取消”、右“确认入账”，等宽。用户于 2026-10-27 明确要求“关闭窗口则直接舍弃”：取消、右上关闭、返回、点击遮罩或手势关闭，均将当前候选标为 IGNORED，不生成账单，也不留为待确认；保留会话和摘要去重标记，防止同一成功页再次弹窗。只有点击“确认入账”才保存。切到其他应用但弹窗仍在、系统临时熄屏或进程异常终止，不等同于用户主动关闭，不自动入账。长内容可滚动，按钮不贴系统导航区。

多个候选排队展示，当前编辑不被抢占。手机锁屏时只保留待确认通知，解锁后由用户进入。拒绝悬浮权限时明确显示“点击通知确认”，不在后台强行启动编辑 Activity。用户也可从采集记录的“待确认”筛选继续处理。

## Shizuku + ADB 后端

1. 接入官方 API / Provider，通过 Binder 生命周期和权限回调更新连接状态。用户安装、启动并授权 Shizuku；ADB 身份通常为 shell，不能据此宣称具备 Root 私有目录读取能力。
2. 使用 UserService 执行固定、只读的前台窗口探测与截图，不提供任意命令输入，不点击或执行支付。Shizuku 模式无需开启轻账无障碍服务。
3. 用户在轻账前台开启采集后，启动明确用途的前台服务。只在亮屏解锁、已选择来源处于前台时有界检查；窗口和配置在截图前后都需匹配，其他应用不进行 OCR。正常交易页最多每两秒处理一次，后台非来源检查退避；暂停、权限撤销、Binder 死亡时立即停止采集和释放连接。
4. 图像通过受控文件描述符流交给主应用，设尺寸 / 时间上限，处理后释放，不写公共相册或持久截图。多屏无法确定目标、安全窗口、空图或不支持的系统接口都显示具体失败状态并跳过。
5. 微信复用现有确认页 / 成功页 OCR、账户缓存、会话去重和直接 / 确认入账决策。Shizuku 只改变数据取得方式，不默认让 OCR 适配所有微信页面。
6. 支付宝继续复用明确支出 / 退款通知规则：Shizuku 模式可独立搭配通知访问权限，不依赖无障碍接收事件。未授权通知访问时显示支付宝通知采集不可用，不把付款页当作到账证明。
7. 首次能力检查失败时不显示“运行正常”，保留可返回无障碍方式的现有入口。更新 / 重启后的服务断开如实反映，不自动申请或代授系统权限。

## 数据升级与验收

- 扩展采集配置和候选字段，迁移保留现有账单与历史，旧配置缺省为直接入账。备份包含新增配置和结构化候选；旧备份兼容；恢复仍暂停自动采集。
- 数据库测试：待确认不计余额、编辑确认生效、各关闭路径舍弃并保留去重、并发一次入账、候选重放合并、切模式不自动提交、旧数据库及备份迁移。
- 通知测试：完整日汇总、退款、转账、跨日和编辑删除刷新，通知频道与 Live Updates 并存。
- Shizuku 测试：未安装 / 未启动 / 拒绝权限 / 断开 / 超时 / 多屏歧义，窗口切换丢弃；测试器真实采集、OCR 及两种入账模式共用去重。
- 构建 Debug、真机安装并回归启动和新增入口；未连接设备或未完成授权时明确列为未验证，不以模拟测试代替 Shizuku 真机验收。

## 官方依据

- [Shizuku API / UserService](https://github.com/RikkaApps/Shizuku-API#userservice)：使用独立 shell / root 身份的进程执行受控任务，跟踪 Binder 生命周期；权限按实际启动身份决定。
- [Android 前台服务类型](https://developer.android.com/develop/background-work/services/fgs/service-types)：长时后台任务需声明适当类型及权限。
- [Android 后台 Activity 启动限制](https://developer.android.com/guide/components/activities/secure-bal)：通知点击或经用户授予的悬浮权限是相关入口，不能假定后台总能直接拉起 Activity。
- [TYPE_APPLICATION_OVERLAY](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#TYPE_APPLICATION_OVERLAY)：应用悬浮窗口使用系统授权的对应窗口类型。
