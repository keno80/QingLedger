# 微信采集可靠性修复计划

用户报告：成功页返回后重复入账、账户时有时无、微信发出转账和红包漏记；收到场景尚未测试，本轮不放开。

证据：正式账本一组同额同商户记录相隔约 18 秒，会话和摘要不同，账户从有变无。代码使用窗口与随机 UUID 建会话，并一次消费付款前账户。真实新转账页事件及截图正常，但容器 `com.tencent.mm.framework.app.UIPageFragmentActivity` 被 OCR 页面白名单拒绝。

- [x] 新增可持久化的付款流程会话跟踪及红灯测试：窗口变化、重进成功页、进程恢复、账户或 OCR 字段缺失不生成新交易；新确认流程允许同额同对方再入账。引用以摘要保存，历史有界，账户不参与去重身份。
- [x] 从已有无障碍账单记录初始化会话引用，避免升级后的首次返回旧页再次入账；不自动删除或合并用户已有账单。
- [x] 保留付款前缓存通过密码 / 验证等中间页，持久化短时结构化上下文；取消、失败、超时、配置 / 来源 / 金额 / 对方冲突仍清除。缺账户显示具体原因，不猜测零钱或银行卡。
- [x] 放开已观察到的微信页面容器，继续要求明确成功状态、唯一金额和页面范围；适配已发出转账的“待对方确认收款”作为支出及对方信息。发出红包仅接受明确的发送成功页面，聊天卡片、领取页和账单历史不触发；实际红包页面仍需样本。
- [x] 领域、独立数据库和 Android 回归，私有转账样本仅本地使用；构建安装后复用用户保留的已成功转账页验证一笔入账与重进不重复，无需再次付款。
- [x] 同步诊断预览、版本、验收记录，暂存全部改动并中文 Conventional Commit 推送。

边界：没有唯一交易号的画面无法绝对区分两笔完全相同的交易；未观察到新确认流程、且结果与已记录页面相同或关键字段缺失时优先复用已有账单。新确认流程提供独立交易证据，不按金额与时间简单合并。只修采集行为，不擅自清理既有重复数据。
