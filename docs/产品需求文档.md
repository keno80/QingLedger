## 1. 产品概述

用户完成支付后，应用从已授权的数据来源识别交易，自动提取金额、收支方向、商户和时间，完成分类、去重并生成账单。信息不足的交易进入待确认列表，用户可以快速修正。

支持普通模式、Shizuku 增强模式和 Root 增强模式。普通用户可以直接使用；有进阶权限的用户可以开启经验证的增强能力。界面采用 Compose miuix，视觉与交互参考 HyperCeiler 的设置项层次、分组方式和主题风格。

本方案默认面向国内个人用户，优先人民币、单人本地账本、无账号使用。产品名称、发布渠道和商业化方式属于方案假设，可在开发立项时调整。

### 核心价值

- 减少忘记记账和重复录入。
- 每笔自动账单能查看来源、识别依据和修正记录。
- 权限失效有明确提示，不把漏记掩盖为正常运行。
- 日常使用以账单和财务概览为中心，权限配置集中在自动记账页面。

### 产品目标与非目标

首版目标是把“授权 → 识别 → 确认 → 统计 → 备份”做完整，提供可实际使用的 Root / Shizuku 接入、状态检测和经验证的增强操作。

首版不包含支付代操作、银行账户登录、交易发起、投资建议、多人共享账本、云端 AI 分析。不承诺所有应用、所有机型或所有交易均可自动识别。

## 2. 用户与使用场景

| 用户 | 需求 | 产品响应 |
| --- | --- | --- |
| 普通 Android 用户 | 支付后少操作、少漏记 | 通知识别、快速确认、手动补账 |
| 未 Root 的进阶用户 | 使用 Shizuku / ADB 增强能力 | 启动向导、授权、能力检测、失效降级 |
| Root 用户 | 使用更多可用的数据来源 | 独立授权、适配器白名单、实验能力开关 |
| 隐私敏感用户 | 财务信息留在设备上 | 离线识别、无强制账号、本地备份与删除 |

典型场景：午餐付款后自动生成餐饮支出；收到转账后确认是收入还是账户间转账；退款后关联原账单；月底查看消费分类和预算；重启设备后发现 Shizuku 未运行并恢复增强模式。

## 3. 产品路线选择

| 路线 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| 普通通知识别为基础，权限按需增强 | 入门简单，权限失败仍可用 | 通知不完整时需要补账 | 推荐 |
| Shizuku 作为强制前置 | 进阶能力入口统一 | 设置复杂，ADB 权限仍有限 | 不作为默认路线 |
| Root / Hook 作为主要采集方式 | 特定适配下可得到更多交易信息 | 覆盖人群有限，适配维护成本高 | 作为后续独立扩展 |

推荐采用统一账单处理引擎和多个采集适配器。Root / Shizuku 改变的是能力来源，不另建一套账本。

## 4. 自动记账能力与权限边界

### 4.1 已核实的技术事实

Shizuku 让普通应用通过以 ADB 或 Root 身份运行的服务访问更高权限的系统 API；ADB 权限有限，并随 Android 和厂商系统变化。因此 Shizuku 的 ADB 模式不能等同于 Root，也不能据此承诺读取任意支付应用的私有数据库。[Shizuku 官方说明](https://github.com/RikkaApps/Shizuku)

Android 提供通知监听服务和无障碍服务，分别支持通知事件和符合条件的界面事件访问。它们都需要相应配置及授权，能拿到的信息依赖应用实际暴露的内容。[通知监听 API](https://developer.android.com/reference/android/service/notification/NotificationListenerService)、[无障碍 API](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService)

以下采集方案属于产品设计与可行性判断；支付应用适配能力必须通过真机验证后才能列为支持。

### 4.2 能力矩阵

| 能力 | 普通模式 | Shizuku（ADB） | Root | 发布要求 |
| --- | --- | --- | --- | --- |
| 手动记账、账单导入、统计 | 支持 | 支持 | 支持 | 不依赖增强权限 |
| 已授权的通知识别 | 支持 | 使用同一基础通道 | 使用同一基础通道 | 通知内容必须包含可解析交易信息 |
| 用户开启的无障碍页面识别 | 后续可选 | 不因授权而自动可用 | 不因授权而自动可用 | 指定页面、指定应用逐项适配 |
| 服务状态与能力检测 | 基础权限检测 | 增加 Binder、身份及实际操作检测 | 增加 su 与实际操作检测 | 不能仅以“已授权”判断可用 |
| 白名单系统设置辅助 | 用户手动设置 | 对允许的操作探测后辅助执行 | 对允许的操作探测后辅助执行 | 显示具体变更并由用户主动触发 |
| 特定系统接口增强采集 | 无 | 可行性验证后开放 | 可行性验证后开放 | 必须有可用接口、适配版本和测试证据 |
| 支付应用私有数据读取 | 不支持 | 不承诺支持 | 仅实验性、逐应用验证 | Root 不保证解密成功或完整性 |
| 应用进程内 Hook | 不支持 | 不作为 ADB 能力 | 需额外框架及适配 | 后续独立模块，Root 本身不等于 Hook |

基础自动记账不要求 Root、Shizuku、无障碍或悬浮窗。增强权限不能替代对采集来源可用性的验证。

### 4.3 Shizuku 接入体验

1. 检查是否安装 Shizuku；未安装时展示官方入口。
2. 展示启动方式。Android 11 及以上可通过无线调试启动；较旧系统使用电脑 ADB 路径，具体兼容范围以实施时验证为准。
3. 引导用户在 Shizuku 内完成启动，再返回应用请求授权。
4. 检查服务连接、授权、运行身份及白名单操作能力。
5. 显示实际可用能力，允许用户单独启用。
6. 服务停止或授权撤销后立即停用对应增强操作，基础通道继续工作。

ADB 启动方式在设备重启后需要重新启动，配对和启动应作为两个不同步骤展示。官方指南也记录了厂商系统造成的启动和权限差异。[Shizuku 启动指南](https://shizuku.rikka.app/guide/setup/)

应用不内置常驻电脑 ADB 依赖，不要求用户开放外网 ADB 端口。设置页展示“ADB 模式”或“Root 模式”，而不是仅显示“Shizuku 已授权”。

### 4.4 Root 接入体验

用户主动选择 Root 模式 → 发起 su 授权 → 检查实际可用能力 → 展示增强项 → 单独开启。

权限拒绝、Root 管理器策略变更或增强适配失败时，退回普通模式。首版的 Root 能力聚焦接入、诊断和经验证的白名单设置辅助；数据采集增强必须另行通过适配验收，不能把权限接通作为采集完成。

## 6. 核心业务规则

### 6.1 识别链路

授权来源事件 → 来源过滤 → 模板匹配 → 字段提取 → 交易校验 → 去重与关联 → 分类与账户匹配 → 自动入账或待确认 → 统计更新。

- 必需字段：正数金额、币种、明确的交易方向或类型、交易时间或可信事件时间。
- 可选字段：商户、支付渠道、资金账户、订单标识、备注、来源应用。
- 金额采用整数最小货币单位存储，人民币按分；禁止浮点金额累计。
- 只有明确成功的交易候选可以自动入账。失败、处理中、营销、余额提示和验证码消息不生成正式账单。
- 同时出现原价、优惠和实付时，优先提取明确标注的实付金额；有歧义则待确认。
- 缺少交易时间时可用事件时间，但应标记为估计；不伪装成精确付款时间。

### 6.2 自动入账策略

提供“全部确认”和“可信交易自动入账”两种策略。首次使用默认全部确认，用户可以主动切换。

可信交易要求：来源和版本在支持范围内、模板完整命中、金额与方向明确、无字段冲突、无重复疑点。未知模板、未知版本或关键信息缺失统一进入待确认，金额缺失时禁止入正式账本。

模板与结构化校验决定可信度。首版不依赖云端大模型，不展示未经校准的“99% 识别可信度”。

### 6.3 分类与账户

分类匹配顺序：用户指定规则 → 已保存商户映射 → 内置关键词 → 未分类。分类不确定而交易本身可信时，可以入账为未分类。

账户匹配顺序：明确账户标识 → 用户配置的来源默认账户 → 未指定账户。支付渠道和资金账户分别保存，“微信支付”不能直接推断为“零钱”。

修正账单时可选择“以后该商户使用此分类”；默认仅修改本笔。P0 支持商户映射，复杂规则编辑器在 P1 提供。

### 6.4 去重与多来源合并

- 有可靠订单标识时，结合渠道、方向、交易类型进行强去重。
- 同一通知的重复回调使用事件标识和内容版本实现幂等；通知更新不能简单视作新交易。
- 缺少订单标识时，使用金额、币种、方向、账户、商户和时间进行候选关联。
- 默认 2 分钟窗口仅用于发现重复疑点，不能只凭“同金额 + 近时间”自动删除账单。
- 同笔交易来自支付通知和银行提醒时，可合并来源证据；证据不足则交由用户确认。
- 两笔相同金额的连续付款必须能够分别保留。
- 用户删除自动账单后保留最小去重标记，防止同一事件重新入账；全量清除时一并删除。
- 用户确认的金额、分类和备注不被后续采集静默覆盖；冲突事件进入待确认。

### 6.5 收支、转账与退款口径

| 类型 | 处理规则 | 统计规则 |
| --- | --- | --- |
| 支出 | 记录实际支付金额 | 计入支出 |
| 收入 | 明确收入才入账 | 计入收入 |
| 账户间转账 | 关联转出与转入账户 | 不计入收入和支出 |
| 提现、充值、信用卡还款 | 不凭关键词直接视为消费 | 默认待确认是否为转账 |
| 退款 | P0 保留为退款候选并人工确认；P1 自动关联原交易 | 关联后冲减支出，不计收入 |
| 红包、收款、报销 | 根据来源和用户规则判断 | 不确定时待确认 |

P0 不自动维护账户余额，避免不完整采集产生错误资产总额。P1 退款采用退款到账日冲减对应分类支出，原交易保留；支持部分、多次退款，累计退款超过原金额时要求确认。跨月退款在到账月份体现，详情提供原交易关联。

正式统计只使用已入账且未删除的记录。待确认、忽略、失败和重复事件不计入。月度结余 = 收入 − 净支出；转账不改变该指标。

## 7. 页面与交互

底部四个入口：账单、统计、自动、我的。记账按钮位于账单页，所有页面中的同类确认、选择与编辑操作保持一致。

### 7.1 首次启动

产品介绍 → 创建默认账本 → 选择需要识别的来源 → 解释通知访问用途 → 跳转系统授权 → 选择入账策略 → 进入首页。

Root / Shizuku 作为可跳过的增强步骤。拒绝授权后仍可手动记账和导入。示例通知测试仅证明本地解析链路；真机来源测试单独标记，不能把演示测试显示为实际支付适配成功。

### 7.2 账单首页

- 顶部：账本和月份选择。
- 汇总卡：本月收入、净支出、结余。
- 轻提示：待确认数量、来源异常或增强模式失效；异常不能遮挡账单。
- 列表：按天分组，展示分类图标、商户、时间、账户、金额和自动来源标记。
- 操作：新增、搜索、类型 / 分类 / 账户筛选；点击查看详情，长按进入批量操作。
- 空状态：分别解释无账单、筛选无结果和自动来源尚未启用。

### 7.3 新增 / 编辑账单

以 miuix 风格底部面板或独立编辑页呈现。先选择支出、收入或转账；金额输入突出，随后选择分类、账户、日期和备注。转账要求转出与转入账户不同。保存后显示简短反馈并支持撤销。

### 7.4 账单详情与待确认

详情展示金额、类型、分类、账户、时间、来源、规则版本及修正记录。来源摘要默认脱敏，需要用户主动展开。

待确认列表按最新事件排序，显示“方向不明确”“疑似重复”“账户待确认”等具体原因，支持确认、编辑、忽略、合并。批量确认仅处理字段完整且无冲突的项目。

### 7.5 自动记账中心

顶部提供全局开关和实际状态：“运行正常”“部分来源不可用”“已暂停”“需要授权”。

分组包含来源管理、通知权限、Shizuku、Root、入账策略和最近识别事件。每个来源展示支持范围、最后收到事件时间、适配版本和错误原因。没有近期事件只显示“暂无新事件”，不推断为故障。

Shizuku 状态包含未安装、未启动、未授权、已连接、能力受限、连接中断；Root 状态包含未开启、不可用、授权拒绝、可用、操作受限。

允许同一设备启用多个通道，但同一增强操作只有一个执行后端。用户可选自动、Shizuku 或 Root；自动模式优先已验证可用的 Shizuku，只有用户已单独授权并启用 Root 时才允许回退到 Root。

### 7.6 统计与我的

统计提供月 / 年切换、分类排行、每日支出趋势、收入与净支出对比，点击图表筛选对应账单。待确认数量单独提示。

我的提供账本、分类、账户、数据导入导出、完整备份、主题、隐私、诊断及关于。无账号入口作为默认设计。

## 8. miuix 视觉规范

本地 HyperCeiler 的依赖为 `fan.miuix`，其设置页使用标题 / 摘要 / 右侧控件结构、分组偏好设置和 DayNight 主题。本项目参考这些结构及风格，自行用 Compose 实现，不直接复制 XML 或资源。

用户提供的 Compose miuix 支持主题和多种组件模块，官方标记为实验性库。实施时固定经过验证的版本，并通过薄封装控制升级影响。[Compose miuix 官方仓库](https://github.com/compose-miuix-ui/miuix)

以下为产品设计起点，不代表从 HyperCeiler 截图测量得到的数值：

| 项目 | 设计要求 |
| --- | --- |
| 整体风格 | 浅灰背景、圆角分组卡片、清晰标题、弱化分割线 |
| 层次 | 财务金额最突出；商户次之；时间和来源为辅助信息 |
| 间距 | 页面横向 16 dp，区块间 12–16 dp，内部 12–16 dp |
| 圆角 | 优先沿用 miuix 组件默认形态，自定义卡片以 20 dp 起步 |
| 字号 | 页面标题约 28 sp，正文 16 sp，辅助 13 sp，汇总金额约 32 sp |
| 颜色 | 蓝色为默认强调色；收支辅以正负号和文字，不只依赖颜色 |
| 主题 | 跟随系统 / 浅色 / 深色，动态配色作为可选项 |
| 交互 | 开关、选择器、弹窗、底部面板优先使用 miuix 对应组件 |
| 动效 | 使用库默认反馈，尊重系统减少动画设置 |
| 可访问性 | 点击区域至少 48 dp，支持字体放大、读屏标签与长商户名 |

账单页保持记账产品的信息密度；自动记账中心和我的页面充分参考 HyperCeiler 的分组设置体验。权限状态使用普通用户能理解的文字，UID、Binder 等诊断信息放在详情中。

## 9. 隐私与数据管理

- 默认本地识别、本地存储，无强制联网、登录和财务信息上传。
- 通知只处理用户选择的来源；其他应用内容不持久化。
- Root / Shizuku 只提供固定白名单操作，不提供任意命令执行接口。
- 原始通知正文默认不长期保存，只保留必要结构化字段和脱敏摘要；诊断留存由用户主动开启，默认 7 天自动清理。
- 关闭来源立即停止新采集；已记账数据保留，用户可以单独删除。
- 导出支持系统文件选择器。CSV 明示为明文；完整备份默认使用密码加密，并包含恢复所需的账单、分类、账户和规则数据。
- 恢复先校验文件与密码，再预览数量和冲突；导入事务失败时不产生半份账本。
- 完整备份跨设备可恢复，不只依赖原设备 Keystore 密钥；未加密 CSV 导出需主动选择。
- 清除全部数据同时删除账单、候选、原始证据、去重标记和应用自管备份；已导出到用户所选位置的文件需告知用户自行管理。
- 应用锁放入 P1；需说明 Root 环境下应用锁不能提供对抗整机高权限访问的绝对保护。

存储和权限实现参照 Android 官方安全建议，具体加密方案由开发阶段验证。[Android 安全清单](https://developer.android.com/privacy-and-security/security-tips)

## 10. 建议技术架构

采用 Kotlin、Jetpack Compose、Compose miuix、Room 和协程 / Flow。产品首期只交付 Android；使用多平台 UI 库不意味着承诺其他平台。

| 模块 | 职责 |
| --- | --- |
| 采集层 | 通知监听；后续无障碍、OCR、Root / 系统接口适配器 |
| 权限层 | Root / Shizuku 接入、能力检测、连接恢复和白名单操作 |
| 识别层 | 来源版本匹配、字段提取、规则校验、分类匹配 |
| 交易层 | 幂等、重复关联、待确认状态、退款与转账关系 |
| 数据层 | 账单、候选、来源证据、账户、分类、规则、备份 |
| 展示层 | miuix 页面、状态反馈、查询与统计 |

事件状态：收到 → 已过滤 / 待确认 / 已入账 / 已关联重复 / 解析失败。候选可被确认或忽略；账单删除与候选忽略分开记录。后台任务用于备份与维护，不用周期任务模拟实时监听，也不通过高频轮询支付应用维持识别。

关键数据对象：

- Transaction：金额、币种、类型、交易时间、时间是否估计、商户、分类、资金账户、渠道、状态、账本、关联交易。
- SourceEvent：来源应用、通道、事件标识、接收时间、解析结果、适配器版本、脱敏摘要。
- Candidate：待确认原因、字段冲突、重复候选、用户决策。
- Rule：来源与版本范围、模板、分类映射、优先级、启用状态。
- Capability：运行后端、授权状态、实际能力、检测时间、失败原因。

支付应用升级后，未知版本应默认关闭未经验证的增强适配器；通知模板未知时仍可生成待确认候选。适配器禁用不影响查看已有账单。

## 11. 异常处理

| 异常 | 用户看到的状态 | 系统处理 |
| --- | --- | --- |
| 通知访问关闭 | 通知来源已暂停 | 停止采集，提供系统设置入口 |
| Shizuku 停止 | 增强模式未运行 | 清理连接，普通通道继续 |
| Root 拒绝授权 | Root 模式不可用 | 不重复弹授权，保留基础功能 |
| 模板未知或字段矛盾 | 有交易需要确认 | 不自动入账 |
| 来源应用无通知 | 暂无可识别事件 | 提供补账入口，不编造账单 |
| 服务中断期间漏记 | 部分时间段可能未采集 | 标记中断时间；无可靠来源时不声称自动补齐 |
| 多来源疑似重复 | 疑似同一笔交易 | 保留候选，提供合并 / 分别保留 |
| 存储写入失败 | 保存失败，请重试 | 回滚事务，候选不标记为已入账 |
| 备份恢复失败 | 文件无效或密码错误 | 保持现有账本完整 |

通知显示默认低打扰：已入账交易可汇总提醒；待确认提醒可关闭。任何提醒均不在锁屏主动暴露完整商户和金额，除非用户选择显示。

## 12. 验收标准

以下为拟定发布门槛，不代表已经达到的实测结果。普通、Shizuku 和 Root 路径分别验收。

| 项目 | 验收条件 |
| --- | --- |
| 基础可用 | 无 Root、无 Shizuku 时可完整手动记账、查询、导出和恢复 |
| 通知采集 | 在明确支持的机型与来源版本上，用真实交易验证收到、解析、入账全链路 |
| 精确性 | 发布样本集中，自动入账记录的金额、币种、方向联合准确率目标 ≥ 99.5%；样本不少于 500 条 |
| 误入账 | 失败支付、余额、广告、验证码等负样本至少 200 条，不得产生正式账单 |
| 幂等性 | 同一事件重复回调 10 次，只产生 1 笔交易 |
| 不误合并 | 同商户同金额连续两笔真实付款，保留 2 笔 |
| 冲突处理 | 同笔交易的金额冲突进入待确认，用户修改不被静默覆盖 |
| 延迟 | 已收到事件后，正常负载下 95% 的解析与持久化在 3 秒内完成；不包含支付应用发通知的延迟 |
| 权限降级 | 撤销授权、停止 Shizuku、拒绝 Root 后不崩溃，状态准确，基础功能继续 |
| 增强有效性 | 每项 Root / Shizuku 能力有实际操作测试；不能仅验证授权弹窗 |
| 数据完整 | 备份恢复后账单数量、金额汇总、分类、账户和规则一致；错误恢复不损坏现有数据 |
| 隐私 | 未启用诊断时，无未选来源持久化和原始全文留存，无财务数据上传 |
| UI | 浅色、深色、大字体、读屏和系统返回均可正常完成核心流程 |

覆盖率与准确率分开统计：准确率评价已自动入账记录是否正确；覆盖率评价受控真机测试中的实际成功交易有多少被正确捕获。通知缺失计入覆盖缺口，不能从分母中剔除后宣传“全部自动记账”。

兼容基线暂定 Android 11 及以上，优先验证 HyperOS 和 AOSP 类系统，再扩展其他 ROM。最终最低版本需结合所选 miuix、SDK 和真机结果确定；不沿用 HyperCeiler 的 Android 15–16 限制作为本产品限制。

## 13. 实施里程碑

### M0：技术可行性验证

验证通知真实样本、Compose miuix 核心页面、Shizuku 连接与白名单操作、Root 授权与操作。输出支持矩阵：机型、ROM、Android 版本、来源版本、可用通道、限制。

门槛：至少一个目标来源可完成真实交易识别闭环；Shizuku 和 Root 各至少一项增强操作验证有效。无法验证的能力不进入正式支持列表。

### M1：可日常使用的首版

交付 P0 全部功能，完成基础记账、通知解析、去重、待确认、统计、权限中心和完整备份。先小范围侧载测试，依据实际使用修正模板；发布渠道选择后再评估其权限与分发要求。

### M2：提高覆盖与账务完整性

交付预算、退款关联、多账本、规则编辑、截图 OCR 和部分导入格式。无障碍页面采集先实验验证，再以可选功能发布。

### M3：独立增强适配

按应用和版本验证 Shizuku 系统接口、Root 采集或 Hook 模块。只有明确增加交易覆盖、且失败可隔离的适配器才发布。工期在 M0 结果确定后估算，不预先承诺全应用覆盖。

## 14. 首版产品决策

1. 普通模式是基础，Root 与 Shizuku 是用户主动开启的增强后端。
2. 自动入账优先保证正确性，信息不足进入待确认。
3. 本地优先、无强制账号、首版不使用云端 AI。
4. 使用 Compose miuix，参考 HyperCeiler 的交互层次并自行实现。
5. 支付来源按实际样本与版本列出支持矩阵，不宣称通用读取能力。
6. Root / Shizuku 接入在首版交付；依赖它们的交易采集增强按可行性结果分阶段交付。
