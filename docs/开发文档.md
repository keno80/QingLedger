## 2. 工程结构与模块依赖

避免首版拆出过多 Gradle 模块。使用 5 个模块，页面按功能包组织。

```text
QingLedger/
├─ app/                         # Application、导航、页面、ViewModel、依赖组装
├─ core/domain/                 # 纯 Kotlin 模型、规则、去重决策、仓储接口
├─ core/data/                   # Room、DataStore、仓储、CSV、备份、维护任务
├─ core/designsystem/           # Compose miuix 主题与少量业务组件
├─ automation/                  # 通知监听、Shizuku、Root、能力管理
├─ gradle/libs.versions.toml    # 固定依赖版本
└─ docs/
   ├─ compatibility.md         # 系统、来源应用和增强操作支持矩阵
   ├─ recognition-rules.md     # 来源模板与规则说明
   └─ backup-format.md         # 备份协议与升级策略
```

依赖方向：`app → domain/data/designsystem/automation`；`data → domain`；`automation → domain`。domain 不依赖 Android、Room 或 Shizuku。automation 通过 domain 接口交付事件，禁止直接写 Room 表。designsystem 不依赖财务业务或权限层。

首版采用手动依赖注入：`AppContainer` 持有数据库、仓储和应用级服务，ViewModel 使用显式 Factory。无需首版同时引入 Hilt / Koin。

## 3. 核心数据模型

### 3.1 通用约定

- ID 使用随机 UUID 字符串；外部订单号不直接作为内部 ID。
- 金额为 `Long` 最小货币单位，人民币按分；输入用十进制解析并检查溢出和小数位。
- 首版只接受 `CNY`；遇到其他币种进入“不支持币种”候选，避免直接混币汇总。
- 时间保存 UTC epoch milliseconds，同时保存交易时区 ID 和是否使用事件时间估计。
- 账本保存统计时区，默认创建时的设备时区；月度筛选转换为 UTC 半开区间 `[start, end)`，不使用字符串截取月份。
- 业务删除使用 `deletedAt`，全量清除执行物理删除；自动来源的最小抑制标记独立保留。
- 分类、账户被交易引用时只能归档，不能直接删除导致历史展示丢失。

### 3.2 数据库表

| 表 | 主要字段 | 约束与索引 |
| --- | --- | --- |
| books | id、name、currency、zoneId、createdAt | 首版仅创建默认账本 |
| accounts | id、bookId、name、archivedAt | 外键 bookId；不保存推断余额 |
| categories | id、bookId、name、kind、iconKey、archivedAt | 收入、支出类别分别管理 |
| transactions | id、bookId、kind、amountMinor、currency、occurredAt、zoneId、timeEstimated、merchant、categoryId、accountId、fromAccountId、toAccountId、channel、note、revision、createdAt、updatedAt、deletedAt | 索引 bookId + occurredAt；金额正数；revision 乐观锁 |
| source_events | id、sourcePackage、profileKey、sourceVersion、channel、sessionKey、contentDigest、receivedAt、occurredAtHint、adapterId、adapterVersion、state、reasonCode、maskedSummary | 唯一 sessionKey + contentDigest；索引 state + receivedAt |
| candidates | id、eventId、parsedFieldsJson、reasonCodesJson、status、resolvedAt | eventId 唯一；字段 JSON 带 schemaVersion |
| transaction_sources | transactionId、eventId | 复合主键；eventId 唯一，防止单事件归属两笔 |
| recognition_rules | id、adapterId、ruleVersion、schemaVersion、definitionJson、enabled | 规则不包含可执行脚本 |
| merchant_mappings | id、bookId、sourceScope、normalizedMerchant、categoryId | 范围 + 商户唯一；首版不跨来源强制同名合并 |
| source_settings | sourcePackage、profileKey、enabled、defaultAccountId、lastEventAt | 与来源版本支持信息分开 |
| dedup_keys | namespace、keyDigest、transactionId、eventId、suppressedAt | namespace + keyDigest 唯一；允许删除交易后仅保留最小抑制信息 |
| transaction_edits | id、transactionId、revision、changedFieldsJson、createdAt | 金额和分类等修正审计，不存原始通知全文 |
| diagnostic_evidence | eventId、encryptedPayload、expiresAt | 用户开启诊断才写入；到期清理 |
| interruption_windows | id、channel、startedAt、endedAt、reason | 记录已知中断；无法确定时使用“未知时间”标签 |

profileKey 使用 Android 用户 / 配置文件范围，首版只支持当前个人配置文件；其他配置文件事件明确过滤，不声称支持工作资料或应用双开。

所有外键处理在 DAO 与事务中定义：账本不允许误删；来源证据删除不级联删除账单；分类与账户使用归档；全量清除按依赖顺序删除。

### 3.3 交易不变量

| 类型 | 必填 | 禁止条件 |
| --- | --- | --- |
| EXPENSE | 金额、币种、时间；分类可用“未分类” | 同时填写转入 / 转出账户 |
| INCOME | 金额、币种、时间 | 同时填写转入 / 转出账户 |
| TRANSFER | 金额、币种、时间、fromAccountId、toAccountId | 两账户相同、跨账本或已归档 |
| REFUND | 原交易关联、金额、到账时间 | 超额退款未经确认 |

P0 解析出退款后只生成候选；用户确认时手动选择原支出，创建独立 REFUND 记录，不修改原支出金额、不计收入。transactions 增加 `refundOfTransactionId`，REFUND 必须引用同账本、同币种且未删除的 EXPENSE；确认前校验累计退款，超额时要求额外明确确认并记录原因。未找到原交易时保持待确认或由用户忽略，不直接入账。

P0 为人工关联提供必要的退款金额校验和到账日冲减统计，沿用 PRD 的 P1 统计口径以避免升级时改写历史。P1 扩展自动关联、部分 / 多次退款操作体验和专用跨月展示。已有退款的原支出删除或金额修改必须同时提示关联退款并校验，不留下孤立关系。

## 4. 核心接口契约

以下是设计契约示例，属于拟建代码接口，不是现有 SDK API。Android 回调和 Shizuku 调用包在平台实现中。

```kotlin
enum class EventChannel { NOTIFICATION, IMPORT }
enum class TransactionKind { EXPENSE, INCOME, TRANSFER, REFUND }
enum class AdmissionPolicy { CONFIRM_ALL, AUTO_TRUSTED }
enum class CandidateReason {
    UNKNOWN_VERSION, UNKNOWN_TEMPLATE, MISSING_AMOUNT,
    AMBIGUOUS_DIRECTION, FIELD_CONFLICT, POSSIBLE_DUPLICATE,
    TRANSFER_REVIEW, REFUND_REVIEW, UNSUPPORTED_CURRENCY
}

data class Money(val minor: Long, val currency: String)

data class SourceEventInput(
    val sourcePackage: String,
    val profileKey: String,
    val sourceVersion: Long?,
    val channel: EventChannel,
    val sessionKey: String,
    val contentDigest: String,
    val receivedAt: Long,
    val fields: Map<String, String>
)

data class ParsedTransaction(
    val money: Money?,
    val kind: TransactionKind?,
    val occurredAt: Long?,
    val merchant: String?,
    val channel: String?,
    val accountHint: String?,
    val externalOrderId: String?,
    val successExplicit: Boolean
)

sealed interface ParseResult {
    data class Matched(val value: ParsedTransaction) : ParseResult
    data class Review(val reason: CandidateReason) : ParseResult
    data class Ignored(val reasonCode: String) : ParseResult
}

interface TransactionParser {
    val adapterId: String
    val ruleVersion: Int
    fun parse(event: SourceEventInput): ParseResult
}

interface ParserRegistry {
    fun select(event: SourceEventInput): TransactionParser?
}
```

解析器是确定性纯函数；不访问数据库、不调用网络、不修改系统权限。fields 只在内存中用于解析，不把整个对象默认序列化到数据库。

仓储与用例契约：

- `ProcessEventUseCase.process(input)`：过滤、解析后调用 EventRepository 的原子决策入口；结果为已过滤、已入账、待确认、已关联或失败。
- `EventRepository.commitDecision(decision)`：内部事务重新检查来源开关、事件唯一键、强去重键和已有交易，确保并发安全。
- `ConfirmCandidateUseCase.confirm(id, edits, expectedRevision)`：重新校验、原子创建或关联账单，再标记候选已确认。
- `SaveTransactionUseCase.save(draft, expectedRevision)`：校验金额 / 类型 / 账户；更新 revision 并写修改记录。
- `MergeCandidateUseCase.merge(candidateId, transactionId, expectedRevision)`：只关联证据；字段差异必须用户选择，不静默覆盖。
- `LedgerRepository.observePage(filter)`：分页返回当前筛选记录；`observeSummary(period)` 返回同口径统计。

所有写用例返回统一 `DomainResult`：成功值或 `ValidationError / Conflict / StorageError / PermissionUnavailable`。异常技术信息写脱敏日志，UI 只显示可操作提示。

## 5. 通知采集与后台生命周期

### 5.1 Android 服务接入

`LedgerNotificationListener` 继承 `NotificationListenerService`。Manifest 中为服务配置 `android.permission.BIND_NOTIFICATION_LISTENER_SERVICE` 和对应 intent-filter；这属于系统绑定保护，不能当作普通运行时权限申请。

授权由系统通知访问设置完成。`POST_NOTIFICATIONS` 仅用于本应用发出提醒，与读取其他应用通知的授权独立。[Android 官方 API](https://developer.android.com/reference/android/service/notification/NotificationListenerService)

处理顺序：

1. 回调立即检查全局开关、来源包名和用户范围；不合格事件在内存中丢弃。
2. 排除本应用通知、分组摘要、无文本事件。
3. 从标题、正文、扩展正文和消息条目取有限字段；每个字段设置长度上限，默认 8 KiB。
4. 生成通知会话标识和内容摘要，在后台协程解析。
5. 事务持久化结构化字段、脱敏摘要及最终状态。
6. 提交成功后再触发汇总提示，不在回调中做导出、Root 请求或长耗时任务。

不读取通知 RemoteViews，不执行通知 PendingIntent，不自动打开支付应用，不取消来源应用通知。

### 5.2 有界队列与崩溃恢复

- 使用应用级 CoroutineScope + 有界 Channel，容量初始 128，单写入消费者。
- 入队失败不能静默丢弃：记录脱敏计数和采集中断状态，提示用户存在覆盖缺口。
- 原文默认只在内存停留；事件事务提交前进程被杀，可能无法恢复，产品明确记录这一限制。
- 不以默认明文原文落盘换取“绝不漏记”。诊断开启后原文单独加密存储，并按 7 天清理。
- `onListenerConnected` 后可以检查仍活跃的通知，走同一去重流程；这不等于恢复已消失的历史通知。
- 通知移除用于结束会话，不删除已入账账单。
- 监听断开记录已知中断起点；连接恢复闭合区间。进程终止造成的未知区间不伪造精确时间。

### 5.3 通知会话与幂等

不能把通知 `key` 永久当作交易 ID：应用可能复用同一通知位置，更新也可能对应不同交易。

- sessionKey 由用户范围、包名、通知 key 和本地会话 UUID 组成。
- 同一活跃通知重复回调沿用会话；移除后重新发布建立新会话。
- contentDigest 对规范化后与交易有关的完整文本字段计算 SHA-256；原文本不随摘要长期保存。
- 同一 sessionKey + digest 是同事件重放，直接返回已有状态。
- 同会话不同 digest 先判断是否补充原交易；明确不同订单标识允许新交易，否则进入冲突或疑似新交易候选。
- 进程重连时按已持久化活跃会话映射进行尽力关联；无法确定的重复只提示，不强行删除。

## 6. 识别、去重与事务入账

### 6.1 来源支持配置

内置适配器描述包含包名、versionCode 范围、语言、通知类型、规则版本、匹配字段、实付标记、方向标记和订单号命名空间。

支付宝与微信是首批验证对象。禁止用猜测的通知内容发布“官方支持”；先采集用户授权的脱敏真机样本，再构造模板。未知模板只在具有交易语义时建立候选，未知广告直接过滤，避免待确认列表泛滥。

首版规则随 APK 发布，不远程下载规则，不执行 JavaScript、Dex 或任意表达式。匹配文本有上限，避免灾难性正则回溯；简单模板优先使用固定词和有限字段匹配。

### 6.2 强去重与弱关联

强去重命名空间由账本、来源交易域、用户范围、币种、交易类型和可靠订单标识组成；存储摘要并加唯一索引。银行卡提醒和支付渠道订单号不默认使用同一命名空间。

弱关联使用 2 分钟窗口加金额、币种、方向、商户和账户。弱关联只产生 `POSSIBLE_DUPLICATE`，不自动合并或删除。

银行扣款与消费通知只有存在明确映射证据时才能自动合并。单纯同金额和近时间保持为两份候选证据，由用户确认。

### 6.3 原子写入

每个来源事件只使用一次短数据库事务完成：

1. 检查来源仍启用且应用未进入恢复 / 清除维护模式。
2. 插入或获取 source_event；已终结的同事件直接返回。
3. 重新查询强去重键和最小抑制标记。
4. 若交易存在且字段无冲突，只关联证据；若冲突，建立候选。
5. 若未知模板、退款 / 转账不明确、信息不足或用户选择全部确认，建立候选。
6. 若可信且策略允许，创建交易、来源关联和强去重键。
7. 更新 source_event 终态；事务提交后刷新 UI。

唯一约束冲突后重新读取已提交结果，不重复创建。事务内禁止 Binder、su、文件导出或长时间规则匹配。

候选确认、合并与忽略也是短事务。两个页面同时确认同一候选时只有第一次成功，第二次返回已处理状态。用户关闭自动记账时增加采集 generation，旧队列任务在提交前校验 generation，保证关闭后不再新增。

### 6.4 手工修正、删除和撤销

- 乐观锁按 revision 校验，旧编辑页面保存时显示冲突，不覆盖新修改。
- 删除交易写 deletedAt，同时保留来源强键和事件抑制标记；统计立即排除。
- 10 秒内提供撤销入口；撤销失败给出明确原因，不只显示成功动画。
- 来源补充不得自动改写用户修正字段；新证据出现矛盾时进入候选。
- 手动交易无来源强键，弱关联可以建议关联到手动交易，但必须用户确认。

## 7. Shizuku 与 Root 实现

### 7.1 状态模型与安全边界

`PrivilegeManager` 输出 StateFlow，状态包含后端、连接、授权、运行身份、每项能力探测结果、最后检测时间和错误码。持久化用户偏好，不持久化“当前可用”作为启动时真值。

| 后端 | 状态 |
| --- | --- |
| Shizuku | NOT_INSTALLED、STOPPED、UNAUTHORIZED、CONNECTED、LIMITED、DISCONNECTED |
| Root | DISABLED、UNAVAILABLE、DENIED、AVAILABLE、LIMITED |

每次操作前重新验证连接与能力；操作超时初始 5 秒，su 授权流程与普通操作超时分开。后台不得主动弹 Root 授权。

Shizuku 通过 Binder received / dead 和授权结果监听器驱动状态；只有 Binder 存活时调用对应 API。依赖与 Provider 配置采用官方 API / provider 模块；Provider 保留官方保护权限，不能随意开放给其他应用。[Shizuku API 指南](https://github.com/RikkaApps/Shizuku-API)

Shizuku 的 uid 为 shell 或 root 时分别展示实际身份，不把 Root 身份的 Shizuku 通道隐藏为普通 ADB。Sui 自动初始化行为也需识别身份并提示，首版不另做 Sui 安装向导。

### 7.2 白名单操作协议

只允许以下操作枚举，不提供 `execute(command: String)` 给 UI、外部 Intent 或第三方客户端：

```text
CHECK_SELF_BATTERY_EXEMPTION
ADD_SELF_BATTERY_EXEMPTION
REMOVE_SELF_BATTERY_EXEMPTION
```

目标包名必须来自本应用 BuildConfig，外部参数不能指定别的包。通过 Shizuku UserService 或 Root 后端执行固定平台操作；首版不得访问支付应用数据目录。

`cmd deviceidle whitelist` 的查询 / 添加 / 移除作为 M0 候选实现路径，必须核对目标 Android 源码、ROM 权限和真实结果后写入兼容矩阵。它不是所有系统都可用的承诺，也不代表厂商自启动权限已开启。

操作流程：检测 → 显示拟变更 → 用户点击 → 执行 → 再查询验证 → 记录结果。失败时打开官方系统电池设置入口作为替代路径，不能以退出码 0 直接宣布设置成功。

撤销仅针对应用自己新增的白名单项；如果启用前已存在则不主动移除。重启、恢复备份或模式切换不自动重放系统变更。

### 7.3 Root 后端

检测 su 可执行文件只说明存在；必须用户发起授权后用实际 UID 与白名单操作确认能力。后端管理进程退出码、输出上限、超时、取消和清理；固定命令在内部生成，任何商户、备注、导入内容不得进入 shell 文本。

Root 不可用时返回结构化错误，保持通知监听运行。应用不安装 Root、不解锁设备、不关闭系统安全功能、不承诺解密第三方数据库。

### 7.4 后端选择

自动模式选择当前已授权、实测可用的 Shizuku；只有用户明确启用 Root 才允许退回 Root。一次操作中途失败不隐式用另一个后端再次变更系统设置，先查询结果并提示用户重试。

连接恢复只重做能力查询，不自动恢复采集增强开关或补执行变更。

## 8. UI 与状态管理

Compose miuix 的主题和偏好组件按官方库使用，通过 `LedgerTheme`、`SettingsGroup` 等少量组件隔离业务。库标记为实验性，应固定版本，升级时检查组件与主题 API。[miuix 官方仓库](https://github.com/compose-miuix-ui/miuix)

不复制 HyperCeiler 的 XML、图片或源代码。参考其“标题 + 摘要 + 状态 / 右侧控件”结构，账单界面自行设计。

| 页面 | UiState | 主要 Intent |
| --- | --- | --- |
| Onboarding | 当前步骤、账本、来源、权限 | 创建账本、选来源、打开系统设置 |
| Ledger | 时段、筛选、汇总、分页列表、空状态 | 搜索、筛选、新增、删除、撤销 |
| Editor | 草稿、字段错误、保存状态、revision | 输入金额、选择分类 / 账户、保存 |

| Candidates | 待处理列表、原因、批处理结果 | 确认、编辑、忽略、合并 |
| Statistics | 时间范围、汇总、分类排行、日趋势 | 切月年、按分类查看账单 |
| Automation | 总状态、来源、权限、能力 | 开关、授权、检测、设置辅助 |

ViewModel 暴露不可变 StateFlow；Compose 按生命周期收集。导航和系统设置跳转使用单次 effect；交易保存结果以持久状态 ID 防止旋转后重复保存。金额草稿用 SavedStateHandle 保存，密码不保存至 SavedStateHandle 或 DataStore。

## 9. 设置、隐私和后台维护

DataStore 保存主题、全局开关、入账策略、后端偏好、诊断开关和首次使用状态。来源开关与账户绑定放 Room，便于事务提交时一致校验。

来源白名单配置须先于解析和日志；主 APK 默认不声明 INTERNET，不包含在线统计 SDK。外部浏览器打开官方链接不要求应用自行下载。

所有普通日志移除金额、商户、正文、订单号和账户标识，只保留错误码、适配器版本与耗时。诊断正文使用 Android Keystore 支持的本地密钥加密，只有用户开启后记录，关闭诊断立即清除正文。[Android 安全建议](https://developer.android.com/privacy-and-security/security-tips)

使用 WorkManager 每日清理过期诊断证据，并在应用启动时补做。事件摘要默认最多保留 30 天；账单关联的结构化来源元信息保留用于追溯，正文仍按诊断周期清除。与已入账或已抑制事件有关的最小去重键独立保留，避免清理摘要后重复入账。

应用重启、系统更新和进入前台时重新检测权限；不设置每秒轮询。通知断开后使用系统支持的重新绑定机制进行有限恢复，不伪造常驻保活或关闭系统安全限制。

## 10. CSV、完整备份与恢复

### 10.1 首版 CSV 协议

UTF-8、标准引用与双引号转义，首行固定列名：

```text
format_version,id,kind,amount_minor,currency,occurred_at,zone_id,time_estimated,merchant,category,account,from_account,to_account,refund_of_id,channel,note
```

`format_version = 1`；occurred_at 为 ISO-8601 带偏移时间；amount_minor 为十进制整数。CSV 只导出正式未删除账单，不导出候选、诊断原文和权限状态。

只支持本应用协议；其他应用或支付账单格式放 P1。分类 / 账户按预览中明确映射，不根据同名静默创建重复对象。转账行必须包含两个不同账户；退款行通过 refund_of_id 引用文件内或本地原支出，先建立 ID 映射再写入，缺少原支出时拒绝该行。错误行显示行号与原因，由用户决定排除后继续或取消。

导入 id 与本地 ID 相同时字段一致则跳过，冲突则提示保留本地或作为新记录。外部文件没有可靠 ID 时采用批次文件摘要 + 行序号防止同文件重导；相似交易只做疑似重复提示。

CSV 导出针对可能被表格应用当作公式的文本加入安全前缀，并在协议中定义可逆转义；导入先反转义，金额等类型列不允许公式。设置导入上限 50 MB、100,000 行，预览超过上限直接拒绝。

### 10.2 完整备份协议

采用版本化二进制容器，外层头部包含 magic、formatVersion、KDF 标识、salt、迭代数、nonce、密文长度；头部作为 AES-GCM 的附加认证数据，防止篡改参数。

- 内容为带 schemaVersion 的结构化 JSON 数据集，包含账本、账户、分类、账单、候选、规则、映射、来源元信息、最小去重标记、修改记录和普通偏好。
- 排除 Root / Shizuku 授权、Binder、活跃通知会话映射、设备密钥、诊断正文和外部文件路径。
- 密码通过 PBKDF2-HMAC-SHA256 派生 256 位密钥；随机 16 字节 salt；初始迭代数 600,000，M0 在目标设备测量后固定写入文件。
- AES-256-GCM、随机 12 字节 nonce、128 位认证标签；每次备份重新生成 salt 和 nonce。
- 密文身份验证完成前不展示可导入记录，不读取未经校验的数据集。
- 文件最大 100 MB，解析头部限制迭代数为 100,000–2,000,000，拒绝异常长度、未知算法和未知未来版本；密码建议至少 8 个字符。
- 密码只在操作期间持有，尽力清理字符数组；不记录、不上传、不承诺 JVM 内存完全不可恢复。

该协议为拟定设计，实施时需使用标准平台加密 API 和固定测试向量验证；不自行实现密码学算法。

### 10.3 一致性与恢复模式

导出从一致数据库快照读取，不直接复制运行中的 Room 主文件。SAF 写入失败不提示成功，尝试清除不完整输出并提示用户检查残留文件。

首版完整恢复只提供“替换当前账本”；CSV 提供合并导入。恢复步骤：

1. 读取并校验容器头，限制文件大小和参数。
2. 解密并验证 GCM 标签。
3. 校验 schema、ID 唯一性、金额、类型、引用关系和统计摘要。
4. 在预览页面展示记录数量、时段、替换影响，用户主动确认。
5. 进入维护模式、暂停采集并递增 generation，阻止旧事件写入。
6. 单事务替换数据库业务数据；事务失败回滚。
7. 普通主题等偏好重新写入 DataStore；如偏好恢复失败，账本保持完整并单独提示，不伪称全恢复失败。
8. 来源采集、自动入账、诊断、Root 和 Shizuku 均保持关闭，重新让用户选择，防止备份触发权限操作。

清除全部数据复用维护模式；完成后生成新默认账本并回到引导。已导出到用户指定位置的文件不能自动删除，提示用户自行管理。

## 11. 统计查询

SQL 只使用 transactions 中 `deletedAt IS NULL` 的正式交易。收入汇总 INCOME，净支出为 EXPENSE 减 REFUND，TRANSFER 排除；REFUND 按到账时间纳入相应时段，并使用原支出的分类。跨月退款允许当前月份净支出为负，不能强行截为零。

同一页面的总额、分类排行和图表使用相同账本、币种、时区和日期边界。日期变化、账单修正、删除和候选确认触发更新；候选数量用独立查询展示。

初期直接使用索引聚合，不引入汇总缓存表。只有真机数据规模测量发现问题，才增加可重建缓存，避免余额和统计双写不一致。

## 13. 验证策略与发布证据

自动化测试只覆盖金额、方向、重复决策、时间边界、事务、恢复和权限状态等关键行为。Room 使用临时数据库验证唯一约束与回滚；Root / Shizuku 用假后端验证业务状态，并用真机验证实际权限能力。

实现后如需要运行单元测试，可针对模块执行，例如 Windows 下 `./gradlew.bat :core:domain:test`。Android 单元与设备测试任务名以工程实际配置为准；运行任何 Gradle 检查都不能在无执行证据时宣称通过，且构建验证仍遵循用户明确要求。

最低兼容验证组合：Android 11 非 Root 设备、当前目标 HyperOS 非 Root 设备、AOSP 类非 Root 设备、Root 设备。每个组合记录实际机型、系统版本、来源 versionCode、Shizuku 身份及结果；没有设备的组合标为未验证，不用模拟结果替代。

首版发布证据必须包括：

- 固定依赖组合与源规则版本。
- 至少 500 条交易样本的金额 / 币种 / 方向联合准确率，目标 ≥ 99.5%。
- 至少 200 条负样本不得生成正式账单。
- 受控实际成功交易的覆盖率，通知缺失计入缺口。
- 回调收到到数据库提交的 P95 耗时目标 ≤ 3 秒。
- 重放、相同金额两笔、并发确认、删除抑制、恢复回滚结果。
- Shizuku / Root 每项开放能力的实际操作与回查证据。
- 深浅主题、大字体、读屏、授权拒绝和服务中断截图或记录。

## 14. 后续扩展约定

P1 的多账本直接使用已预留 bookId；预算独立表，不改交易来源链路。退款扩展增加自动关联和专用展示，复用 P0 的 REFUND 记录及到账日统计，已有人工确认记录不能再次生成退款。

OCR 和无障碍以新 EventChannel 接入，只提供结构化候选；来源权限与白名单分开授权。Root / Hook 适配器不得复用设置辅助接口来绕过范围限制，需独立能力清单、精确支持版本和默认关闭开关。

数据库升级保留显式 migration 与迁移测试，禁止 destructive migration 删除用户账本。备份 schema 和规则 schema 独立版本化，未知未来版本拒绝导入并提示升级。
